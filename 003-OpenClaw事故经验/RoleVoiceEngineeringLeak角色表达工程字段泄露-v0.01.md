# 角色表达工程字段泄露事故经验｜v0.01

日期：2026-07-26

## 现象

少主要求贾南风执行模拟通知验收后，收到两类工程化回复：

1. 贾南风主 Agent 把测试卡、执行者、约束和验收条件直接列给少主。
2. `WorkboardNotificationRelay` 固定发送事件 ID、Card ID、英文状态、worker 摘要、heartbeat/proof 等内部字段。

这违背了项目已有的角色定位：内部可以工程化办事，面向少主应保持各角色自己的语言。

## 根因

- 线上 `systemPromptReport` 证明贾南风正确加载自己的 `AGENTS.md`、`SOUL.md`、`IDENTITY.md` 等文件，且没有截断；因此不是串用角色卡。
- 现有角色文件只写了人格和“直接答复”，没有明确区分内部工作记录与少主沟通成稿。模型受到当前工具和工作板上下文影响，直接复用了内部术语。
- Relay 是无模型确定性脚本，不经过角色卡。其固定模板本身就是工程报告，所以角色卡无论多完整都不能改变第二条通知。

## 修复原则

- 共同协议 v0.08 建立“内部工作面 / 少主沟通面”。
- 八个 Agent 的 `SOUL.md` 固定现有角色声音，`AGENTS.md` 给出子 Agent 也能独立执行的输出规则和正反例。
- 内部 Task/Card/run/event/heartbeat/proof 继续完整保留；默认不对少主展示。
- 少主明确索要技术细账时，先给角色化自然结论，再单列原始技术字段。
- Relay 自己实现确定性的賈南風呈现器，并保留原始事件/audit 作为工程证据。
- 不采用全局消息重写 Hook，避免所有自由文本被统一模板误改。

## 防回归

- 八个 Agent 新 session 必须分别验证正确 workspace、零 bootstrap 截断和角色回复。
- housekeeper、ops、reviewer 追加技术细账测试。
- Relay 必须通过语法检查、16 项自测、四类终态预览、禁词检查、真实 Workboard→Telegram 链路和重复发送检查。
- 角色化不得改变事实、权限、风险、状态或验收结论。

## 已验证结果

- 八角色普通回复全部保持各自现有角色锚点，没有泄露内部工程字段。
- 三个技术角色先给自然结论，再单列技术细账。
- 真实卡片 `eea17b56-fdd0-403b-80c1-0fe7bd82d247` 完成后，Relay 只发送一次：

```text
少主，本宫盯着的「新通知表达」已经办妥。
```

- Telegram message ID 为 401；随后待发事件为 0。
