# CodexResetWatcher 单源延迟事故经验 v0.01

- 事故日期：2026-07-26
- 影响：重置消息比 Tibo 的 X 原始动态晚约 55 分钟送达
- 修复范围：CodexResetWatcher

## 1. 发生了什么

Tibo 在 03:17:12 发布 X Post `2081096447718723984`。旧 Watcher 在 03:42:16 正常运行，却只读取 `codexreset.org`，网站当时尚未收录，因此返回 `NO_REPLY`。04:12:16 下一轮才从网站发现，04:12:34 Telegram 送达。

这不是 Cron 漏跑，而是需求和验收都被错误缩减成“网站可访问、网站能解析、Telegram 能发送”。之前明确要求的“核查网站和 X 最新动态”没有被完整实现和验收。

## 2. 根因

1. **设计缺口**：单一网站被当作 X 动态的替代，而不是独立来源。
2. **调度叠加延迟**：网站公开刷新周期约 1 小时，旧 Watcher 再以 30 分钟轮询，最坏发现延迟可进一步叠加。
3. **验收缺口**：没有用一条已知 X Post 验证“发现、官方核验、网站缺席、去重和发送”的完整链路。
4. **健康状态缺口**：旧状态只记录最后事件和 `seenIds`，无法区分 X、网站或发送链路是否健康。

## 3. 正确做法

- 将“发现”和“事实验证”分离：无凭据时可用公开 RSS 发现候选，但必须由 X 官方 oEmbed 验证已知 Post。
- 网站只作为独立交叉核查和降级路径，不能阻塞已经通过官方验证的直接事件。
- 有 X Developer 凭据时优先 X API v2；Token 只从 `0600` 文件读取，不进入命令参数、日志、状态或聊天。
- 两个发现源分别记录成功和失败；两者同时失败必须让 Cron 真实失败。
- 测试必须覆盖单源失败、双源失败、普通 Post、网站尚未收录、重复 ID、旧状态迁移和真实 Telegram。

## 4. 后续验收准则

凡需求写明“网站 + X 最新动态”，验收证据必须同时包含：

1. 最新 Post 的 ID、作者、发布时间、正文和原始 URL；
2. 官方 X 验证结果；
3. 网站是否已收录；
4. 网站尚未收录时是否仍可形成待通知事件；
5. 两个来源各自故障时的行为；
6. Telegram 成功后去重状态的实际变化。

只证明网站可访问，不能再宣称“X 最新动态监控已完成”。
