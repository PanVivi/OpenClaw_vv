# RiskNotice 最小正式修复计划 v1.00

> 日期：2026-08-13  
> 目标版本：OpenClaw `2026.7.1-2 (0790d9f)`  
> 生产基线：`workflow-governance 1.2.0`，`dist/index.js` SHA-256 `96bc4f7c9ef9433533512c62b785076cc42887e6c621cbcd147a510c2234c828`

## 一、这次只解决什么

取消没有判断价值的人类逐命令批准。对现有 `workflow-governance` 已识别的高风险工程命令，改成以下固定顺序：

1. 原动作先停下，不执行。
2. 夏姬用三个全新的独立会话，针对同一份完整资料，按顺序审核三次。
3. 只有三次都明确通过，才由贾南风向少主发送一条事前告知。告知不要求回复。
4. Telegram 明确返回消息编号后，原执行 Agent 才能把参数完全相同的动作重试一次。
5. 任一审核不通过、超时、格式不合格，或通知没有确认送达，都不执行并保留原因。

## 二、明确不做什么

本次不扩展为通用安全平台，不接管 root、SSH、人工 CLI、Gateway 管理 RPC、其他插件或 OpenClaw 之外的操作；不新建密钥服务，不重构全部工具，不修改角色人格、身份和核心职责。保护范围仍是现有插件拦截的、由 `riskAgentIds` 中 Agent 通过 `exec` 或 `process` 发起且已关联正式工作单元的命令。

因此，本改动是生产工程流程中的风险过滤和留痕，不宣称能抵御恶意管理员、绕过插件的外部命令或模型之间完全相同的系统性盲点。

## 三、依据与现场事实

- 官方执行审批说明表明审批可以按安全级别和询问策略配置；现场已经是 `security=full, ask=off, askFallback=full`，所以无需再扩大权限，只移除插件自己向少主索要“同意”的流程。
- 官方插件 Hook 支持在 `before_tool_call` 阶段阻止工具调用；现有插件正使用该入口，保持原入口最小改动。
- 官方 Plugin SDK 提供 `runtime.subagent.run` 和通道 outbound adapter；固定使用 `deliver:false` 的 reviewer 会话，并由 housekeeper 的 Telegram account 发送告知。
- 生产源码已读回核对：高风险当前为 `pending_decision → approved → executing`，错误后又回到 `approved`；这两处分别改为三审告知和失败后禁止自动重试。
- GitHub issue 与社区经验共同说明：自治能减少机械式确认，但重启、长任务、并发与会话恢复仍容易产生误判。因此三审只作为降低漏判概率的措施，执行前仍要核对备份与回退资料，并保留审查、通知和执行结果。

## 四、最小代码改动

### 4.1 高风险记录

沿用 `workflow-risk/v2` 文件和现有串行写入队列，只给高风险记录增加：

- `preflight`：准确范围、可核验备份、回退办法；
- `reviews`：三次审核的序号、独立会话键、运行编号、结果摘要、时间；
- `notification`：贾南风告知正文摘要、Telegram 消息编号、发送时间；
- `reviewRunId`：一次审核流程的随机编号，用来拒绝并发流程和迟到结果；
- 状态：`preflight_required`、`reviewing`、`review_blocked`、`notified`、`executing`、`completed`、`execution_failed`。

原来的 action fingerprint、planId、workUnitId、Agent 和会话归属继续使用。参数变化会产生新 fingerprint，必须重新走完整流程。

### 4.2 新增一个内部动作

在现有 `workflow_governance` 工具中新增 `review_high_risk`，仅允许最初发起该记录的工程 Agent 在同一正式工作单元调用，并必须提交：

- 被拦截时返回的 action fingerprint；
- 本次动作的白话范围；
- 已核验备份；
- 可执行的回退办法。

插件核对记录和归属后，在现有串行状态更新中只允许一次 `preflight_required → reviewing`，同时写入不可变 `reviewRunId`。第二个并发调用直接拒绝。以后每一条审核、草拟和通知结果回写都必须同时核对当前状态与 `reviewRunId`；迟到结果不得改变新状态。`review_blocked`、`completed`、`execution_failed` 都是不可逆终态。没有备份或回退资料时直接拒绝。

### 4.3 夏姬三次独立审核

插件按顺序启动三次 `agent:reviewer:risk-<随机值>` 新会话，每次都：

- 接收同一份完整资料：目标、影响、最坏情况、替代办法、准确范围、备份、回退、动作摘要；
- 不接收前一次审核输出；
- `deliver:false`，不向外发消息；
- 插件在启动前登记该会话和 `reviewRunId`，并用高优先级 `before_tool_call` 内层前置闸门拦截该会话的任何工具调用；不能只依赖提示词或事后检查；
- 要求只返回严格 JSON：`approve` 或 `block`、理由和发现；
- 任何工具调用、启动失败、超时、无回复或格式错误都视为不通过。

只有三次均为 `approve` 且没有发现，状态才可继续。三审是三次独立采样，能够减少偶发漏判，但不包装成绝对安全保证。

### 4.4 贾南风事前告知

三审通过后，插件让贾南风在新的内部草拟会话中生成白话正文。该会话同样先登记到本次 `reviewRunId`，使用 `deliver:false`，并由同一个内层前置闸门在工具执行前拒绝所有工具调用。正文必须符合她的角色语气，且包含：

- 准备做什么；
- 会影响什么；
- 最坏可能怎样；
- 出问题如何退回；
- 已由夏姬独立审核三次；
- “这是事前告知，不用回复，我会按计划继续”；
- 预计开始时间。

正文不得出现命令、路径、指纹、会话编号、内部卡片名或工程缩写。插件校验正文后，先再次核对记录仍为同一 `reviewRunId` 的待通知状态，再明确使用 housekeeper 的 Telegram account 发给现有少主账号；只有适配器返回非空 `messageId` 且回写时状态和运行编号仍匹配，才记为 `notified`。发送失败或结果不明时停止，不自动补发，也不执行。

### 4.5 只放行一次

工程 Agent 收到内部结果后，只能重试参数完全相同的原动作。`before_tool_call` 在现有串行状态更新中把 `notified` 改成 `executing` 后放行；后续同 fingerprint 调用一律拦截。`after_tool_call` 成功记 `completed`，报错记 `execution_failed`，不再恢复成可执行状态，防止失败后重复产生副作用。

### 4.6 三份角色规则

只增加行为规则，不改人格：

- 鱼玄机：不再向少主索要命令批准；被高风险门拦下时，提交范围、备份、回退给内部流程；三审和告知完成后只重试原动作一次。
- 夏姬：每次审核都视为独立完整审核，不参考前次结论；资料不足或有未解决风险就阻止，不为了凑三票而通过。
- 贾南风：事前告知使用自然中文和角色语气，不问“是否同意”，不展示工程内部信息；整个任务完成后仍按原流程发送最终完成通知。

## 五、实施顺序与回退

1. 从生产机备份 `workflow-governance` 目录、插件配置和三份角色规则，并记录 SHA-256。
2. 在隔离工作树中以生产 `1.2.0` 为基线同步源码、manifest、README 和测试，不从仓库旧 `1.1.0` 直接覆盖生产。
3. 完成代码和角色规则后运行构建、单元测试、集成测试、`git diff --check` 和秘密扫描。
4. 先部署可热加载的插件与角色文件，不主动重启 Gateway。若现场证明必须重启，停止本轮上线，先把重启作为新的高风险动作另行处理，不借本计划自动扩大授权。
5. 部署后若健康检查、Telegram、任务系统或既有插件异常，立即恢复第 1 步备份；恢复后再次核验服务与通道。

## 六、验收标准

以下全部满足才算完成：

1. 低风险动作仍自动执行；中风险仍内部预检，不询问少主。
2. 高风险动作初次调用没有副作用，并要求提交范围、备份和回退。
3. 三次审核使用三个不同新会话，顺序执行，任何一次不通过都不发事前告知、不执行。
4. 两个并发 `review_high_risk` 只能启动一组三审；迟到审核或草拟结果不能覆盖终态。
5. 夏姬三次审核会话和贾南风草拟会话都为 `deliver:false`，主动尝试任何工具时会在工具执行前被拒绝且没有副作用。
6. 三次都通过后，贾南风发出的正文为白话、符合角色语气、不要求回复、不含命令或内部编号。
7. Telegram 没有有效 `messageId` 时动作不执行。
8. 参数完全相同的动作只放行一次；参数变化必须重新三审；执行报错不得自动重试。
9. 使用一条“文字包含高风险关键词、实际仅打印验收标记”的无害命令做生产端到端测试，证明三审、告知、一次放行和日志留痕；不真实重启、不改数据、不开放网络。
10. `openclaw status --all`、Telegram probe、任务系统、Gateway 稳定性和插件状态无回退。
11. 文档记录实现边界、三次计划审核、测试证据、生产备份、部署结果和回退方法，并同步 GitHub。
12. 全部完成后，由贾南风发送最终完成通知。

## 七、三次计划审核规则

本文件哈希冻结后，由夏姬用三个全新会话按顺序审核三次。每次都审核完整文件，但只判断以下四件事：

1. 是否准确实现本次用户目标；
2. 是否与 OpenClaw `2026.7.1-2` 已核对的接口一致；
3. 是否存在会导致未通知就执行、重复执行或无法回退的明显缺陷；
4. 是否越出第二节的明确边界。

任何一次发现问题就修订本文件、重新冻结哈希，并从第一次审核重新开始。三次全部通过后才允许实施。
