# 晨报接手与 Telegram 工作流修复｜全模块控制与賈南風转交修订｜v0.01

修订日期：2026-08-09（Asia/Taipei）  
适用计划：`MorningBriefAndWorkflowRepair正式修复计划-v0.01.md` 与 `MorningBriefAndWorkflowRepair晨报定稿修订-v0.01.md`  
修订原因：现场证明蕭觀音只会建立独立提醒，不认识既有晨报，也没有把对话信息写入晨报模块；少主进一步明确，所有允许数据输入的模块都必须由蕭觀音正确维护，并兼容賈南風代收后转交蕭觀音完成录入。

## 1. 新增完成定义

本次不能以“角色文件写了晨报”“Skill 已安装”“JSON 可手工编辑”或“賈南風已发送一条 A2A 消息”作为完成。必须同时达到：

1. 系统中只有一个正式晨报定义；蕭觀音能查询它的启用状态、固定 06:00 计划、最近运行、最近投递和当前停用原因，不再用通用提醒数量推断晨报数量。
2. 少主直接对蕭觀音说出模块信息后，蕭觀音能识别目标模块，调用专用工具写入，工具完成 schema 校验、去重、原子落盘并返回可读回执；蕭觀音必须回读后再说“已经记好”。
3. 少主对賈南風交代相关信息时，賈南風只能建立持久的晨报转交记录并触发蕭觀音处理；最终数据写入必须由 life 侧专用操作完成。转交状态必须从 `pending` 到 `applied` 或 `blocked`，没有 `applied` 回执不得说“已经录入”。
4. 七个正文模块以及抬头/问候中所有允许人工维护的输入均有明确入口；自动事实字段保持只读，不能因“全模块可输入”而允许手工伪造天气、空气、农历、任务运行事实或门人在线状态。
5. 日程事件的一个录入事务同时决定晨报展示和提醒策略。所有非默认事件默认提前 60 分钟单独提醒；事件发生时间和提醒时间分别保存，不能再次混为一谈。
6. 直接录入、賈南風转交、修改、取消、重复消息、过期、Gateway 重启、插件重载和晨报读取均有自动测试及生产真实对话验收。

## 2. 机制选择与版本边界

生产版本仍为 `OpenClaw 2026.7.1-2 (0790d9f)`。2026-08-09 重新 `git fetch` 后，GitHub 远端最新项目提交仍是 `origin/codex/fix-life-memo-permission` 的 `88659057a4d1abc5f9ec7ce992c03a138523a220`；本独立工作树从同一提交开始，远端 `main` 较旧，不能倒退对准。

按照官方 Tool / Skill / Plugin 分工，本次采用四层：

- 角色文件：只写职责、自然语言和何时使用专用能力；不承担数据一致性。
- 晨报控制 Skill：把自然语言意图映射、澄清条件、写后回读、转交处理和失败表达写成短操作手册；不作为唯一执行保证。
- 晨报控制 Plugin：提供 typed Tool、字段校验、原子状态、事件提醒、转交状态和审计，是强制数据边界。
- `hehuan-daily`：只读经过验证的晨报输入存储并与自动事实合并，确定性生成定稿；06:00 仍由唯一 command Cron 触发，不让模型“记得运行”。

插件优先使用当前生产版本已由 `life-automation` 验证可用的 `api.runtime.subagent.run`，以固定 life requester/session 唤醒蕭觀音；不让 housekeeper 模型临场选择目标。若维护诊断改用 `sessions_send`，必须遵守官方的 inter-session data / `isUser=false` 来源语义。无论采用哪条唤醒通道，授权来源、原始范围、去重键和失效时间都先存入转交记录，life 只凭 `handoff_id` 读取并应用，不能接受唤醒消息正文夹带的新范围。

## 4. 数据模型与输入边界

所有动态记录都必须包含稳定 ID、`source=direct_life|housekeeper_handoff`、已认证来源时间、创建/更新时间、适用日期或失效条件、状态和去重键。写入使用同目录临时文件、`fsync`、原子替换、父目录同步和进程锁；损坏时 fail-closed 并保留隔离证据。

| 显示区域 | 蕭觀音可写内容 | 自动只读内容 | 冲突规则 |
|---|---|---|---|
| 抬头与晨辞 | 称呼、语气、问候偏好、临时祝语及有效期 | 公历、星期、农历日期 | 偏好只改变表达，不改日期事实 |
| 天候司 | 当日/区间目的地、出行时间、天气关注备注 | 温度、体感、湿度、降水、风、日出日落、天气代码 | 地点先地理解析；多结果必须澄清，不允许手填天气数值冒充实测 |
| 清气监 | 敏感人群偏好、户外活动安排、空气关注备注 | AQI、颗粒物、趋势和来源类型 | 用户感受可作为备注，不能覆盖监测/模型值 |
| 衣行令 | 怕冷/怕热、通勤方式、着装禁忌、随身物偏好 | 由天气推导的基础建议 | 偏好与天气共同生成，冲突时说明理由而非静默覆盖 |
| 宗门脉象 | 少主交代的生活待办、状态、截止日、晨报显示范围 | Workboard/Task 的系统运行事实 | 人工待办标明来源；不能把口头“完成”伪装成系统任务成功 |
| 门人名录 | 指定日期的门人相关备注、需要关注事项 | Agent/account/session 在线与活动事实 | 人工备注单列；在线数只取核验源，缺源则明确未核实 |
| 今日玉牒 | 事件、时间、地点、状态、重复规则、取消和提醒策略 | 固定排班投影 | 用户事件与排班合并去重；非默认事件默认提前 60 分钟提醒 |
| 今日小签 | 显示/隐藏偏好、签语风格、当天寄语备注 | 农历、干支、节气、宜忌、冲煞 | 不能手工改农历或黄历事实；寄语与事实分层显示 |

所有区块即使没有事实也保留定稿框饰，并用角色化中文说明“暂无已确认内容”或“尚在核对”；不得省略区块，也不得用 `[待确认]`、null、source id 或内部字段填充。

## 5. 专用工具契约

### 5.1 `morning_brief_control`（仅 `agentId=life`）

支持：

- `inspect`：返回唯一晨报登记、预期 Cron、最近运行/投递、当前停用原因、输入版本与待处理转交数；敏感路径和 chat id 不返回给模型。
- `get_day`：按本地日期回读最终会进入各模块的人工输入与提醒摘要。
- `upsert_event` / `cancel_event`：创建、修改、取消日程；保存事件时间与提前提醒分钟，默认 60；同去重键幂等。
- `upsert_task` / `set_task_status` / `archive_task`：维护生活待办，不直接修改系统任务真相。
- `set_location` / `clear_location`：按日期范围解析和维护目的地；解析结果不唯一时返回候选并停止写入。
- `set_preference`：只接受模块白名单键和值类型。
- `upsert_note` / `archive_note`：为任一模块维护有日期范围的用户备注，不覆盖自动字段。
- `apply_handoff`：只接收 `handoff_id`，从插件私有记录读取已认证范围，完成同样校验和写入；不接受附加 payload。

每个写操作的工具结果必须包含 `ok`、是否实际变化、记录 ID、影响模块、进入晨报的日期、提醒时间/状态和写后摘要。失败返回自然可转述的缺项，不回显敏感路径、栈或整段原消息。

### 5.2 `morning_brief_handoff`（仅 `agentId=housekeeper`）

支持 `submit/status/cancel`。`submit` 必须包含模块、动作、最小结构化字段、少主授权来源时间、范围、失效时间和去重键。插件先持久化为 `pending`，再唤醒固定 life 会话；life 使用 `apply_handoff` 后插件才标 `applied`。超时或工具失败标 `blocked` 并回告賈南風，不自动重复可能有副作用的应用。

housekeeper 不能调用 life 的直接写工具，也不能把 `pending` 说成完成；life 不能要求少主重复已认证且范围未变的正式转交。

### 5.3 事件提醒

晨报控制插件按 15 秒以内的固定 tick 检查事件提醒，状态持久化并在 Gateway 重启后恢复。到时只通过固定 life requester/session 和 life Telegram account 投递一次角色化提醒；提醒有独立 idempotency key、`pending/sent/unknown/failed` 状态。`unknown` 禁止自动重发。该路径取代“先用通用 `life_automation` 建事件发生时刻提醒、再靠模型补改”的不可靠组合。

## 6. 应用读取与合并

`hehuan-daily` 新增只读输入加载器，与现有 owner profile 分离：owner profile 继续提供固定排班和默认地点；动态输入文件只提供可变事项。加载器必须：

1. 验证固定 owner 根、普通 JSON、非符号链接、0600、schema 版本和大小上限。
2. 按目标本地日期过滤事件、任务、备注、偏好和地点覆盖，忽略已取消/归档/过期记录。
3. 将排班与用户事件合并、排序、去重；日程显示事件发生时间，不把提前提醒时间当事件时间。
4. 将模块备注作为有来源的补充行；天气、AQI、农历、系统任务与在线状态仍从自动事实源取得。
5. 七个模块固定渲染；空数据走各模块自己的角色化空态。
6. 任何动态输入损坏只降级人工输入并发一条角色化失败说明，不使用旧缓存伪装最新事实，也不破坏自动天气/空气/农历生成。

## 7. 角色与 Skill 修改

- life `AGENTS.md` / `TOOLS.md`：明确“合欢宗晨间玉简”是唯一晨报、当前状态从专用 inspect 查询、所有模块输入先走专用工具、写后回读、非默认事件提前 60 分钟、正式转交无需二次索权。

- Skill：同时覆盖 direct-life 与 housekeeper-handoff 两条路径，列出最少澄清字段、模块映射、去重、修改/取消、过期和自然回复示例。
- 角色表达继续遵循现有设定；用户侧不显示 JSON、tool、job、路径、UUID、Cron 或内部状态词。技术细账只有少主明确索要时另列。

## 10. 回滚与不能假称完成的事项

- 插件或角色更新失败：恢复旧文件和配置键，Gateway 受控重载；晨报 Cron 保持 disabled，不恢复错误版发送。
- 动态输入迁移失败：保留原 owner profile 和 life-automation，不删除用户既有非晨报提醒；新输入文件隔离并停止读取。
- 转交通信失败：记录保持 pending/blocked，賈南風自然说明未录入，不自动重复应用。
- Telegram 提醒或晨报返回 unknown：停止自动重发，人工核对。
- OpenClaw 2026.7.1-2 上游完成投递缺口仍只能由本地持久状态缓解；没有真实消息回执时不得宣布完全根治。
- 门人在线数和宗门系统任务若没有稳定事实接口，允许模块保留角色化空态与用户备注；不得为满足华丽版式伪造数字。该事实源缺口若仍存在，最终单独列出。
