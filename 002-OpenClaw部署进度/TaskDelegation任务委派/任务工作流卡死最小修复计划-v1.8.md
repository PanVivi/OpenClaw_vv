# 任务工作流卡死最小修复计划 v1.8

日期：2026-08-16  
状态：完成通知链修订稿；本稿重新三审通过前不得部署。  
范围：仅 `task-system-control`、两个收据工具的精确 allow 项、测试、必要部署脚本和本次运维文档。

## 一、结论与边界

现网卡死不是人工审批或原生命令权限造成的。任务已登记并生成工作单元，但没有实际执行会话；插件仍把任务显示为“运行中”。原链路 `主角色 → 角色控制 Agent → Workboard → 执行 Agent` 有两个模型委派环节，并把只读诊断也封住。

当前插件是 path 安装的外部插件。OpenClaw 官方明确拒绝此类插件使用 `api.runtime.gateway.request()`，因此本次不再让新任务依赖 Workboard/Gateway，而改成官方允许外部插件使用的 `api.runtime.subagent.run()`：

`主角色 → task-system-control 持久计划 → 目标角色执行 Agent`

不修改 `workflow-governance` 的重大风险三审、夏姬身份、贾南风白话事前通知和 Telegram 留证规则；不升级 OpenClaw，不改模型路由及其他业务模块。

## 二、受支持的执行通道

1. 每个任务包确定性生成一个工作单元；目标、完成标准、能力和前置结果直接写入执行提示。包依赖仍由插件确定性控制。
2. 新工作单元通过生产版本已存在的 `api.runtime.subagent.run({sessionKey,message,lane,lightContext,deliver,idempotencyKey})` 启动，不指定 provider/model，不使用生产版本尚无契约的 `toolsAlsoAllow`。
3. 新增插件独占工具 `task_work_proof`、`task_work_complete`。部署时只把这两个精确名称加入八个角色现有 `tools.allow`；不添加核心工具、不移除底层 deny。每次启动前读取有效配置核对目标 Agent 确实可见这两个工具，缺一项就拒绝启动并如实 blocked。
4. 删除 `dispatchGatewayMethod`、Workboard 转发 HTTP 路由和所有新任务的 Gateway/Workboard 调用。旧 Workboard 记录保留，不删除、不重放。

## 三、新状态机与防重复

状态 schema 升为 v3；v2 原始证据全部保留。新计划/包标记 `delegationMode: direct_subagent_v3`，旧记录标记 `legacy_controller_v2` 或 `legacy_workboard_v2`。

### 3.1 启动与相关性

1. `waiting_dependencies`：前置包未完成。
2. `ready`：unit 已持久生成，尚未认领。
3. `starting`：在一次状态事务内写入唯一 link、不可猜测 `launchNonce`、`generation=1`、稳定 idempotencyKey，以及永不跨 unit/generation 复用的 `agent:<target>:subagent:task-system-<unit>-<nonce>`。
4. 生产兼容探测证实，本机 2026.7.1-2 的 `api.runtime.subagent.run()` 经 `agentRunTracking: plugin_subagent` 返回 Gateway 已接受的 `runId`，并登记结束追踪，但此调用路径不发出 `subagent_spawned`。因此调用方输入的唯一 childSessionKey、generation/nonce 与服务端接受的 runId 通过一次 CAS 合并后进入 `running`；不得再等待该路径不会出现的 spawned 事件。
5. `subagent_spawned` 仍作为未来版本的兼容观察信号；若出现，必须同时匹配 agentId、sessionKey、generation/nonce 与 runId。不一致只进入 `reconcile_required`，不得另启执行。
6. API 明确返回前的超时、断线、进程中断或缺 runId 进入 `reconcile_required`，禁止自动再次 run；API 已返回后以 runId、固定 session 和 `subagent_ended.targetSessionKey` 做终态对账。极短任务若先收到 ended：按精确 childSessionKey 命中当前 generation/nonce，把 ended runId、outcome、endedAt 暂存在同一 link；API 返回后在同一 CAS 中比较 accepted/ended runId 并合并终态。不一致则 quarantine，绝不重跑；即使 API 随后报 timeout，已匹配的 ended 仍证明旧 run 存在并按收据规则收口。
7. 两个并发 reconcile 只有第一个能在串行状态事务中取得 claim；其余只读当前结果。所有写入都以 revision 与 generation 做 CAS。
8. direct worker 由持久 link 的精确 sessionKey 识别，不再依赖 `:subagent:workboard-` 前缀。它不进入 Telegram intake、不触发主会话 finalize 重委派、不受 main/controller veto；accepted/spawned/ended 必须以 runId、sessionKey 和 generation 唯一命中同一 link。

### 3.2 Unknown 与重新执行

- `reconcile_required` 只允许读取固定 session 消息、匹配 spawned/ended 事件和已有 run/session 证据。
- 只有强证据确认旧 run 从未创建，才能由专门恢复动作建立 `generation+1`；普通 reconcile 不能解除 unknown。
- 无法证明旧 run 不存在时，只能继续 quarantine 或 cancel。若业务必须重做，另建新恢复任务，并在说明中标注旧执行可能迟到；不复用旧 unit/session/nonce。

### 3.3 收据与终态

- proof/complete 请求必须携带 workUnitId、generation、launchNonce；插件同时核对当前 agentId、精确 worker sessionKey、当前 claim 和允许的非终态。
- 迟到事件、错误 session、旧 generation、已取消或任一终态均拒绝写入。
- link、unit、packet、plan、inbox 五层终态单调，普通 reconcile、迟到收据和迟到结束事件都不能退回 starting/running。
- 只有 successful outcome、proof、completion 三者齐备才 succeeded。成功结束但收据暂缺先进入 `reconcile_required`；显式 reconcile 做一次有界核对，仍缺才 blocked，避免结束事件与最后收据乱序。
- 收据正文限长并清洗敏感字段；状态保存摘要、哈希和时间，不保存令牌或完整命令环境。
- 前置结果摘要写入后继 packet 的 `inputRefs` 和 worker 提示。若 `subagent_ended` hook 中 runtime 不可用，只把后继置 ready，由显式 reconcile 启动；`gateway_start` 永不自动重放。

## 四、旧状态迁移优先级

按以下顺序命中，前项优先：

1. succeeded/cancelled/failed/blocked：保持终态。
2. 有旧 Workboard link 或真实 worker run/session：标记 legacy_workboard_v2，只接受匹配的旧收据/结束事件，不创建 direct worker。
3. controller 被实时任务证据证明仍存活，或 lease 未过期且结果未知：标记 legacy_controller_v2，禁止 direct。
4. controller 已确认结束，或 lease 已过期且已有 decompositionReceipt：历史 controllerRunId 不算 active；若已有 unit 且无 link/run/session，可显式 reconcile 转 direct。只把与 v2 控制器已知模板逐字段完全一致的记录认作通用占位：`unitKey=***`、title=`执行并验证角色任务`、objective=`继承原任务包上下文,闭环完成范围确认、核心实施、结果验证和验收证据整理。`，且四条 completionCriteria 与冻结模板完全一致；实现中保存这组规范字段的固定 SHA-256，并以测试固定。命中时把 title、objective、completionCriteria、capability、inputRefs、agentId 全部改为所属 packet 的对应值，以 `packet.targetAgentId` 为唯一 session 目标，并重新执行 `capabilityRule(packet.capability, packet.targetAgentId)`；不匹配即 quarantine。任何不完全命中该指纹的专用 unit 均不覆盖，异常角色/能力也不启动。
5. lease 已过期、无 decompositionReceipt 且无法证明 controller 是否启动：quarantine/reconcile_required，不自动 direct。
6. 无 controller、无 link/run/session 的 ready 孤儿 unit：显式 reconcile 后建立 direct claim，只启动一次。
7. 无 unit 且没有 live/unknown controller 的 pending 包：显式 reconcile 后确定性生成一个 direct unit。

`decompose_packet` 只接受 legacy_controller_v2；direct 包拒绝再次拆分。`gateway_start` 只迁移和报告，不启动 controller/worker。源码权威基线为隔离工作树中的 TypeScript；现网手改 dist 仅作故障证据。版本统一升为 2.1.0，package、manifest、README、源码、dist 与测试保持一致；弃用配置字段保留一版兼容。

## 五、进度必须说真话

- 只登记成功：“已登记，尚未启动”。
- 已 claim 但证据不完整：“正在核对是否已启动”。
- 本机该调用路径取得 Gateway accepted runId，且唯一 session/generation/nonce CAS 齐全：才说“已经开始执行”；未来若出现 spawned 信号继续做一致性核验。
- 明确校验/执行失败：五层同步 blocked/failed，并返回 `ok:false`。
- reconcile 返回 started、running、succeeded、blocked、unresolved 数量；存在 unresolved 时不得只返回笼统 `ok:true`。

逐层映射固定为：确定执行失败时 link/unit=`failed`，packet/plan/inbox=`blocked`；结果未知时 link/unit=`reconcile_required`，packet 保持非运行等待态，plan/inbox 对外显示“正在核对”而不是 running；取消和成功保持各自终态。

## 六、权限简化

- 主会话不再被本插件额外禁止 `read`、网页检索、记忆检索；提示词同步改为“可只读核对，具体变更必须委派”。
- 继续阻止 exec、process、write/edit/apply_patch、Gateway、message 和业务变更工具。
- sessions_list/history/send/spawn 继续限制，避免跨角色会话泄露或绕过工作流。
- 只撤销本插件自己的 veto，不改变 OpenClaw 的 tools.allow、deny、workspace/sandbox、会话可见性、渠道身份与角色权限。

## 七、完成通知与 Telegram

生产源码核对证实，`runHeartbeatOnce()` 在角色 heartbeat 关闭或没有周期时会直接 `skipped: disabled`，`requestHeartbeat()` 也不能使该事件执行。因此不启用周期心跳、不再排队完成 system event，也不再用模型生成完成通知。

改用生产版本已公开在插件 runtime 的 `api.runtime.channel.outbound.loadAdapter("telegram")`，由插件通过 `accountByAgent.get("housekeeper")` 对应的贾南风 Telegram 账号直接发送固定白话模板。收件人只取已鉴权 owner inbox 的 `senderId`，并与 `ownerTelegramId` 再核对；不得取或回退到 `ctx.channelId`。正文只含任务名称、成功/停止、可理解的结果或原因和“详情已有留档”，不含 Card、runId、session、路径、哈希等工程字段；语气固定为贾南风角色口吻。这样没有额外模型调用，也不依赖 Gateway 请求特权或 heartbeat。

发送状态机固定如下：

1. 先只读加载 Telegram outbound adapter，确认 `sendText` 存在、owner `senderId` 与 `ownerTelegramId` 一致、贾南风账号配置完整；这一步没有外部副作用。预检不通过创建或更新 `kind=completion_direct` 的唯一记录为 `failed_before_dispatch`，没有调用 adapter。
2. 预检通过后，在同一次持久状态事务内按 `eventKey=task-plan-completion:<planId>` 创建不可变 `kind=completion_direct` 的唯一 outbox 项，并写入随机 `attemptId`、`generation=1`、`status=acquired`、正文哈希、owner senderId 和贾南风 accountId。只有成功创建 claim 的回调可以发送；并发或重复终态回调只读已有项，不调用 adapter。若已有 `failed_before_dispatch`，只有显式 reconcile 在重新预检成功后可用 CAS 把同一记录改为新的 `attemptId`、`generation+1`、`status=acquired`；并发 reconcile 仍只有一个 claim 持有者。
3. 发送可带稳定 `deliveryQueueId=eventKey` 只作日志相关性。生产 Telegram raw `sendText` 不消费 `deliveryQueueId/onPlatformSendDispatch`，它们不提供 provider 幂等、是否已发送或可重试证据。返回带 messageId 才按 attemptId/generation CAS 为 `sent` 并写 `completionWakeAt`；返回缺 messageId 或抛错一律 CAS 为 `unknown`，保留 attemptId/错误，禁止自动重发。只有 Telegram/宿主耐久投递记录能明确证明该 attempt 未发送，才可由显式 reconcile 建立 `generation+1`；“没有 messageId”或 deliveryQueueId 均不是强证据。无法证明时只留待人工核对。
4. 旧 `queue_notification/message_sending/message_sent` 路径只处理不可变 `kind=ordinary_agent`；`queue_notification` 拒绝 `task-plan-completion:` 命名空间，两个消息 hook 也不得查询或改写 `completion_direct`。完成通知不经过普通消息 hook，其 `failed_before_dispatch/acquired/sent/unknown` 只能由 direct sender 按 attemptId/generation CAS。`sent`、`unknown`、`acquired` 均拒绝第二个发送者，且终态不可降级。
5. v2→v3 通知迁移保守处理：所有缺少 `kind` 的旧 outbox 保留原 status、contentHash、messageId、error 和时间，补为 `kind=ordinary_agent`；若旧记录的 eventKey 已占用 `task-plan-completion:` 保留命名空间，则标为 quarantine 并报告，绝不解释成 `completion_direct`。旧 PlanRecord 的 `completionWakeAt` 是 system event 实际处理前写入的旧语义，不能证明 Telegram 已发送；旧终态计划若没有同 eventKey 的 `completion_direct status=sent` 且带 messageId，一律迁移为 notification unknown/quarantine，保留旧时间作证据，禁止自动补发，也不得对外声称已通知。只有人工核对 Telegram/宿主耐久记录后处置。

本次不承诺“网络故障时既绝不漏又绝不重”；在 provider 没有公开幂等保证时优先避免重复 Telegram，并把不确定性如实留档。重复结束事件不得重复通知。

## 八、测试与生产验收

### 自动测试

- 构建、类型检查、有效集成测试和 workflow-governance 回归通过。
- devDependency 与测试运行时固定为生产补丁版本 `openclaw@2026.7.1-2`；生产版本 SubagentRunParams 契约测试；不传 toolsAlsoAllow/provider/model；八角色有效配置均含两个 receipt allow 项。
- direct worker 被精确识别为 worker，不误判 main/controller；direct 包拒绝 decompose。
- 并发 reconcile 只产生一个 claim/一次 run；claim 后中断、commit-then-timeout、缺 runId 均 unknown 且不重跑。
- generation/nonce fencing、accepted runId、无 spawned 的生产路径、ended-before-run-return 合并、迟到 spawned/ended/receipt、五层终态单调测试。
- 旧 controller 占位指纹逐字段固定；命中后 unit 的 title/objective/completionCriteria/capability/inputRefs/agentId 与 packet 完全一致并重新校验角色能力，且 packet 与原 inbox 目标不偏离；非完全命中的专用/异常 unit 不被覆盖或启动。
- 成功结束与最后收据乱序测试；依赖只激活一次且 inputRefs 进入提示。
- v2 各类 legacy、当前 orphan、live/expired/unknown controller 按迁移优先级测试。
- 主会话 read/web/memory 不被本插件拦截；写入/执行/跨会话仍被拦截。
- 完成通知并发终态回调只产生一个 outbox claim/一次 adapter send；adapter 预检失败、`failed_before_dispatch` 显式恢复的 generation CAS、发送成功带 messageId、返回无 messageId、发送抛错、发送后进程中断、重复终态、显式 reconcile 均按上述状态机测试，`unknown/acquired/sent` 不自动重发，只有 `sent` 写 completionWakeAt。
- ordinary_agent 与 completion_direct 互不命中测试；`queue_notification` 拒绝完成命名空间，message hooks 不能改写 completion 项，direct sender 不能改写 ordinary 项。
- v2 outbox 缺 kind 的迁移保留原状态/回执并归为 ordinary_agent；旧记录占用完成命名空间时 quarantine；只有旧 completionWakeAt 而无 completion_direct sent+messageId 时迁移为通知 unknown/quarantine、重启后不自动补发；对应迁移夹具和重启测试固定。
- mock 与生产同版本契约测试确认 `api.runtime.channel.outbound.loadAdapter("telegram")` 和 `sendText` 存在，调用严格使用贾南风 accountId、经 ownerTelegramId 核验的 inbox.senderId；确认 deliveryQueueId 只作相关性且不被当成幂等/投递证据；源码与 dist 无 `runHeartbeatOnce`、完成 system event、内部 Gateway、Workboard 新调用和废弃 HTTP 路由。
- package、manifest、README、config schema、`contracts.tools`、`toolMetadata` 与 dist 同为 2.1.0；旧 controller 配置字段仍能校验但不再驱动新任务。
- 部署前在生产同版本运行时做一次非 mock 兼容探测：启动唯一无害 direct worker、取得 accepted runId/固定 session；确认该调用路径是否发 spawned，并按实测契约关联；确认两个收据工具真实可调用且没有新增其他核心权限。

### 生产证据链

部署前记录 OpenClaw、Node、插件精确版本、有效配置校验、插件/配置/状态 SHA-256、权限与属主；备份到 `/Volume3/OpenClaw/home/.openclaw/backups/task-system-control-2.1.0-<UTC>/`。部署使用同目录临时文件原子替换。

代码回滚默认只恢复插件代码、manifest/package 和两个 allow 项；状态只做只读快照，不在已有新 run 后盲退。若状态污染，先停止新入口、核对执行会话，再定向修复。

真实验收：

1. 对当前生产状态快照的副本做离线迁移，确认旧占位 unit 精确继承 packet 边界且只会产生一个 claim；生产原备忘录计划只保留/取消，不再以它触发业务修改或后继任务。
2. 在生产已有 owner inbox 下创建一个唯一命名、单包、无后继、只读的验收计划，逐项核对 inbox、plan、packet、unit、direct link、generation/nonce、accepted runId、固定 session、可选 spawned 一致性、真实输出、双收据及五层成功终态。
3. 在隔离临时目录执行一次低风险写入，确认无需人工批准、内容正确并清理。
4. 重大风险只做不会执行破坏动作的拦截回归，确认夏姬三次记录、贾南风事前通知和 Telegram messageId。
5. 最终 Telegram 有成功记录和 messageId；缺任一证据不宣布通过。

## 九、部署重启与停止条件

先确认是否支持热加载。若必须重启 Gateway，它是本次唯一计划内重大风险动作：三次复审通过、备份和回滚准备完成后，由贾南风在重启前用白话 Telegram 说明目的、短时影响、最坏情况、回滚办法和即将重启，并保存 messageId。恢复重启包含在同一通知范围。出现重复执行、Gateway 不稳定、Telegram 失联、receipt 工具不可见或风险门禁回归失败时立即停止。

## 十、明确不做

- 不把插件伪装成 trusted official，不扩大 Gateway 权限。
- 不重构 RiskNotice，不改变重大风险判定与审批规则。
- 不删除旧 Workboard 数据、其他 AI 工作树、草稿或 SSH 临时密钥。
- 不顺带修备忘录、晨报、模型、移动端或其他模块。
