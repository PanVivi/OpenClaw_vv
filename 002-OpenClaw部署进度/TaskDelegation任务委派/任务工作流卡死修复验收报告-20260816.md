# 任务工作流卡死修复验收报告

日期：2026-08-16
生产环境：OpenClaw 2026.7.1-2 / Node.js v22.14.0
插件：task-system-control 2.1.0

## 结论

修复已部署并通过真实只读验收。

原设计确实过于复杂、权限边界也过度收紧。旧链路是“主角色 → 控制 Agent → Workboard → 执行 Agent”，一个任务要经过两次模型委派；控制 Agent 没有成功产出工作单元时，状态仍可能显示运行中。插件还额外拦截了主会话的读取、网页与记忆核对，导致只读调查也反复撞墙。

新链路收敛为“主角色 → 持久计划 → 目标角色 direct subagent”。主会话恢复只读核对，实际执行和写入仍必须委派；重大风险三审、夏姬身份、贾南风事前白话通知和 Telegram 留证规则没有放宽。

## 调研依据

- OpenClaw 官方 Plugin SDK runtime、hooks、subagents 文档确认外部插件可以使用 subagent runtime，但不能冒用 trusted-official Gateway 权限。
- 官方与源码合同确认 Telegram outbound adapter 的 `sendText` 使用 `cfg/to/text/accountId` 并返回 messageId；housekeeper heartbeat 关闭时，`runHeartbeatOnce` 和 `requestHeartbeat` 不能承担本次完成通知。
- GitHub 相关问题显示 system event/heartbeat、子 Agent announce 和异步投递存在已知边界，因此完成通知改为贾南风账号的确定性直发，不启用周期 heartbeat，也不增加一次模型调用。

## 实施内容

- 新任务不再依赖 Workboard/controller，直接启动目标角色 subagent。
- 每个 unit/generation 使用唯一 session、nonce、runId CAS；超时或结果未知禁止自动重跑。
- proof、complete 和 successful outcome 三者齐备才成功；link/unit/packet/plan/inbox 五层终态单调。
- 只允许插件独占的 `task_work_proof`、`task_work_complete` 两个收据工具加入八角色 allow，不扩大核心工具权限。
- 主会话恢复 read/web/memory 只读核对；exec、write/edit/apply_patch、业务变更和跨会话绕行仍被阻止。
- 完成通知由 Telegram outbound adapter 使用贾南风 accountId，严格发送给已核验 owner senderId；不使用 inbox.channelId。
- completion_direct 与 ordinary_agent 分账；唯一 outbox claim 防并发重复。没有 messageId 或发送异常时记 unknown，绝不自动重发。
- 旧 outbox 和旧 completionWakeAt 保守迁移；旧时间不再被误认为 Telegram 已送达，也不会自动补发。
- 已结束 inbox 不能被重新 triage、建计划、转交或追加模块。
